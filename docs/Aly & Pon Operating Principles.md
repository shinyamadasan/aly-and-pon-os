# Aly & Pon Operating Principles

## Scope

These principles primarily guide the Business Knowledge Base, but they also define the boundaries between the Business Knowledge Base, Product Lab App, and Git repository.

## Purpose

The Business Knowledge Base exists to preserve and organize Aly & Pon's business knowledge.

It is not an operational system.

## Principle 1 - Single Source of Truth

Each type of information has exactly one owner.

| Information | Owner |
| --- | --- |
| Brand strategy | Notion |
| Product positioning | Notion |
| Content planning | Notion |
| Business decisions | Notion |
| Inventory | Product Lab App |
| Recipes | Product Lab App |
| Costing | Product Lab App |
| Purchases | Product Lab App |
| Production | Product Lab App |
| Sales | Product Lab App |
| Code | Git |
| Knowledge base schema | Git |

## Principle 2 - One Purpose Per Page

Every page must answer one clear question.

Examples:

- Brand Bible -> Who are we?
- Product Catalog entry -> What are we selling?
- Content Library entry -> How are we communicating it?
- Decision Log entry -> Why did we change?

If a page serves multiple unrelated purposes, it should be split or simplified.

## Principle 3 - Knowledge Over Operations

Notion stores:

- Ideas
- Strategy
- Documentation
- Decisions
- Positioning
- Content knowledge

Notion does not store:

- Inventory
- Recipes
- Production
- Costing
- Purchasing
- Daily operations

## Principle 4 - Simplicity Wins

When choosing between adding another database or improving an existing page, prefer improving the existing page unless there is a recurring need for database behavior.

## Principle 5 - Relationships Explain Context

Relations exist to answer questions like:

- Why was this product renamed?
- Why was this series created?
- Which decision changed this product?

Relations should improve understanding, not recreate operational workflows.

## Principle 6 - Grow Only When Necessary

Do not build for future possibilities.

Add pages, databases, and automation only after recurring work demonstrates the need.

## Principle 7 - Document Decisions, Not Conversations

Do not preserve raw discussions by default. Preserve conclusions.

Bad pattern:

- We discussed six logo ideas.

Good pattern:

- Selected Logo Concept B because it communicates warmth while remaining simple.

## Principle 8 - Improve From Use, Not Elaboration

Every improvement to the Business Knowledge Base must be justified by actual usage or a clear business need, not by the desire to make the workspace more elaborate.
